# Native RAG — отчёт о текущей архитектуре и результатах

## Область отчёта

Этот документ описывает только RAG-часть проекта: загрузку документации, разбиение на фрагменты, индексацию, retrieval, выбор активного контекста, соседнее расширение, объединение spans и механизм кэширования префилла.

Оценка генерации и сравнение генеративных моделей намеренно не входят в этот отчёт.

В проекте термин «Native RAG» означает конкретную архитектуру этого репозитория: внешний корпус документации обрабатывается как память, а в рабочий контекст попадает только ограниченный набор выбранных фрагментов.

## 1. Краткий вывод

Текущая система уже является рабочим прототипом Native RAG для обычных текстов и документации.

Её главное отличие от простого классического RAG — не сам BM25 и не наличие dense-поиска, а разделение на три уровня:

1. полный внешний корпус, который не помещается в рабочий контекст;
2. широкий пул кандидатов, в котором ищутся потенциально полезные фрагменты;
3. ограниченное active window, которое реально передаётся дальше.

После выбора active window фрагменты префиллятся один раз и используются через кэш. Поэтому размер внешнего корпуса не должен напрямую превращаться в размер KV-cache.

По текущим retrieval-only тестам:

- на синтетическом корпусе в 1M токенов все 8 иголок попали в активное окно во всех 3 эпизодах;
- на 30-сэмпловом MRCR-тесте все ответы имели хотя бы один целевой фрагмент в выбранном контексте;
- точное сохранение конкретного первичного чанка после расширения составило 29/30;
- основная зона дальнейшей работы — не базовая способность находить релевантную область, а повышение точности и покрытия при ограниченном бюджете.

## 2. Архитектура

```text
Markdown / TXT
      │
      ▼
Структурное разбиение
      │
      ▼
Небольшие индексируемые chunks
      │
      ├── BM25 / lexical index
      └── optional native dense index from the same GeneratorBackend
              │
              ▼
        Retrieval candidate pool
              │
              ▼
   Adaptive span selector
   ├── anchor chunks
   ├── соседние chunks
   └── coalesced spans
              │
              ▼
        Ограниченное active window
              │
              ▼
  PromptSpec → GeneratorBackend → chunked prefill → model-native cache → рабочая сессия
```

## 3. Что делает каждый слой

### 3.1. Загрузка и разбиение документации

Сейчас поддерживаются `.md`, `.markdown` и `.txt`.

Разбиение учитывает:

- абзацы;
- границы предложений;
- заголовки Markdown;
- overlap между соседними chunks;
- источник и активный заголовок каждого фрагмента.

Заголовок не дублируется в тексте фрагмента, но сохраняется как metadata и участвует в retrieval. Фрагменты разных файлов не смешиваются при соседнем расширении.

Текущая схема использует размер chunk в символах, а не строгий token-aware budget. Это удобно для подготовки читаемых фрагментов, но является одним из технических ограничений, которое стоит устранить перед финальной калибровкой.

### 3.2. Lexical retrieval

Базовый retrieval — детерминированный BM25 без обязательной внешней нейросети.

Перед индексированием выполняются:

- Unicode NFKC-нормализация;
- приведение к нижнему регистру;
- нормализация `ё` в `е`;
- разбор дефисных и апострофных слов;
- удаление небольшого набора стоп-слов;
- boost точного совпадения фразы;
- boost совпадений с заголовком.

Это хороший базовый слой для документации с точными названиями разделов, параметров, сущностей и терминов. Он прозрачен, быстр и воспроизводим.

### 3.3. Optional dense и hybrid retrieval

Проект также содержит `DenseIndex` и `HybridRetriever`.

Dense-представления не являются отдельной моделью retrieval. Если текущий GeneratorBackend предоставляет native-dense capability, они строятся из скрытых состояний той же загруженной языковой модели. Если capability отсутствует, система работает в BM25-only режиме. Lexical- и native-dense-ранжирования объединяются через Reciprocal Rank Fusion.

При этом retrieval-only тесты, приведённые ниже, намеренно используют BM25 CPU-only. Это позволяет отдельно проверить саму механику поиска и active window, не маскируя результат дополнительным dense-слоем.

### 3.4. Candidate pool и active window

Ключевое решение — не путать глубину поиска с объёмом передаваемого контекста.

Например:

- `candidate-k = 128` означает, что retrieval может посмотреть на 128 кандидатов;
- `budget = 8192` при чанках по 128 токенов означает максимум 64 малых chunks;
- в active window попадут только выбранные 64 chunks, а не все 128 кандидатов.

Это позволяет искать глубже, не раздувая рабочий контекст.

### 3.5. Neighbor expansion

После нахождения anchor-фрагментов система может добавить соседей с тем же источником.

Цель — восстановить локальную структуру документа, если ответ пересекает границу chunk или использует ближайший контекст. Соседи выбираются только вокруг уже найденных anchors и не переходят границы файла.

Важный компромисс:

- больший radius повышает локальное покрытие;
- но соседние chunks занимают бюджет и могут вытеснять независимые anchors;
- поэтому соседнее расширение должно рассматриваться как boundary repair, а не как замена retrieval.

### 3.6. Adaptive span selector

Текущая двухуровневая схема работает так:

1. retrieval ищет по маленьким chunks;
2. в active window сохраняются выбранные anchors и допустимые соседи;
3. только реально выбранные последовательные chunks объединяются в spans;
4. далёкие независимые anchors не теряются из-за принудительного coarse-разбиения.

Например, при `chunk_tokens = 128` и `span_size = 2` соседняя пара может передаваться как один читаемый span примерно на 256 токенов. При этом бюджет считается в малых chunks, а не по количеству итоговых spans.

Это лучше простого правила «всегда склеивать документ в крупные блоки»: крупный coarse chunk может захватить много мусора и одновременно ухудшить recall далёких независимых фрагментов.

### 3.7. Кэширование и рабочее окно

Кэширование не определяет релевантность, но является важной частью практической архитектуры.

Текущая схема:

1. retrieval выбирает active window;
2. выбранный контекст подаётся кусочками через chunked prefill;
3. backend формирует model-native cache, который переиспользуется на последующих шагах;
4. внешний корпус остаётся вне prompt и вне KV-cache.

Таким образом, корпус на 250k или 1M токенов не обязан превращаться в KV-cache такого же размера. В память рабочего процесса попадает только выбранный контекст, плюс служебные структуры индекса.

## 4. Сравнение с обычным RAG

| Аспект | Типичный классический RAG | Текущий Native RAG |
|---|---|---|
| Единица поиска | Часто сразу фиксированный top-k крупных chunks | Малые chunks для точного поиска, spans только после выбора |
| Объём поиска | Часто совпадает с объёмом передаваемого контекста | Candidate pool шире active window |
| Размер внешнего корпуса | Обычно не подаётся целиком, но бюджет часто задаётся косвенно | Явно отделён от ограниченного рабочего окна |
| Соседний контекст | Часто отсутствует или добавляется грубо | Добавляется локально вокруг конкретных anchors |
| Границы документов | Могут случайно смешиваться | Соседнее расширение не пересекает source-файлы |
| Крупные фрагменты | Нередко фиксируются заранее | Объединяются только среди уже выбранных соседних chunks |
| Retrieval | Часто обязательный dense/vector DB | Рабочий lexical BM25; dense — опциональный слой |
| Дообучение retriever | Может использоваться | Не требуется для базового режима |
| Длинный внешний корпус | Обычно требует предварительного уменьшения до top-k | Может оставаться внешней памятью при малом active window |
| KV-cache | Обычно соответствует полному prompt конкретного запроса | Содержит только выбранное active window |
| Воспроизводимость | Зависит от dense/search backend | BM25-слой детерминирован и легко диагностируется |

Главная разница — не в том, что классический RAG обязательно «плохой». Классический RAG хорошо решает задачу «найти несколько релевантных фрагментов». Native RAG добавляет к этому отдельный механизм управления рабочей памятью: искать можно глубже, чем реально помещать в активный контекст.

## 5. Фактические результаты

### 5.1. Синтетический multi-needle на 1M токенов

Параметры:

- внешний корпус: `1,000,000` токенов выбранного tokenizer;
- 3 эпизода;
- 8 иголок в разных позициях от начала до конца корпуса;
- по одному похожему draft-фрагменту на каждую иголку;
- active budget: `8192` токенов;
- малый chunk: `128` токенов;
- `span_size = 2`;
- `candidate_k = 128`;
- `neighbor_radius = 1`.

Результат:

| Метрика | Значение |
|---|---:|
| Seed recall иголок | 100% |
| Active-window recall иголок | 100% |
| Полное покрытие иголок | 100% |
| Эпизоды со всеми 8 иголками | 3/3 |
| Выбранных малых chunks | 64 |
| Итоговых spans | 61 в среднем |
| Precision по target chunks | 15.6% |
| Время CPU | 2.21 с за 3 эпизода |

Это контролируемый синтетический тест, а не доказательство качества на произвольной документации. Он подтверждает другое: при корпусе в 1M токенов текущий selector способен одновременно удержать несколько далёких целей в фиксированном active window.

Низкий показатель precision ожидаем: 8 иголок распределены по широкому окну из 64 chunks, а соседнее расширение добавляет локальный контекст. Для практического RAG precision нужно измерять вместе с полезностью соседних фрагментов, а не считать любой непомеченный chunk бесполезным автоматически.

### 5.2. MRCR retrieval-only, диапазон до 256k

Параметры последнего 30-сэмплового retrieval-only прогона:

- 30 samples;
- 8needle MRCR;
- исходные prompts из диапазона до 256k токенов;
- active budget: `8192` токенов;
- малый chunk: `128` токенов;
- `span_size = 2`;
- `candidate_k = 128`;
- `neighbor_radius = 1`.

Результат:

| Метрика | Значение |
|---|---:|
| Seed recall первичного target chunk | 30/30 = 100% |
| Recall после adaptive expansion для первичного chunk | 29/30 = 96.7% |
| Seed recall любого target chunk | 30/30 = 100% |
| Recall любого target chunk после expansion | 30/30 = 100% |
| Среднее покрытие target chunks | 39.2% |
| Среднее contiguous-покрытие | 30.9% |
| Среднее число выбранных малых chunks | 64 |
| Среднее число spans | 57.3 |
| Средняя context precision | 2.34% |
| Средний seed rank | 22.77 |

Интерпретация:

- первичный retrieval уверенно находит область ответа;
- adaptive expansion сохраняет хотя бы часть целевого контекста во всех 30 samples;
- полное покрытие длинных target-областей пока далеко от идеала;
- active window содержит заметно больше контекста, чем строго целевые chunks.

Последний пункт показывает текущий главный компромисс: система хорошо удерживает recall, но платит за это precision и неполным покрытием больших ответных областей.

#### Что означает context precision = 2.34%

Это не процент правильных ответов, не вероятность найти иголку и не показатель того, что ошибка возникает в середине текста.

В текущем retrieval-only benchmark метрика считается так:

```text
context_precision = число выбранных target chunks / число всех выбранных chunks
```

При active budget `8192` и малом chunk `128` система выбирает `64` малых chunks. Например:

```text
1 target chunk из 64 выбранных = 1.5625%
3 target chunks из 64 выбранных = 4.6875%
```

Среднее `2.34%` означает, что в среднем в выбранном наборе было около `1.5` chunks, которые пересекались с узко размеченной target-областью, из 64 выбранных.

Остальные chunks не обязательно являются бесполезным мусором: часть из них — соседи, нужные для связности текста, а часть — независимые lexical anchors, которые selector сохранил из-за широкого candidate pool. Но строгая метрика засчитывает как «точные» только chunks внутри размеченной target-области. Поэтому она специально штрафует соседнее и дополнительное покрытие.

В этом MRCR-наборе target-область занимает несколько последовательных chunks, а её положение меняется от sample к sample: она может быть в начале, ближе к центру или в хвосте исходного текста. Число `2.34%` усредняет состав выбранного окна, а не положение ошибки.

Для понимания системы нужно читать эту метрику вместе с другими:

- `any_target_chunk_recall = 100%` — хотя бы часть нужной области найдена во всех samples;
- `mean_target_coverage = 39.2%` — в среднем покрыта примерно треть размеченной target-области;
- `context_precision = 2.34%` — выбранное окно значительно шире узкой target-разметки.

Иными словами, текущий RAG хорошо находит район ответа, но пока приносит слишком много дополнительного контекста относительно строгой разметки.

## 6. Сильные стороны текущей версии

1. **Понятная диагностика.** Можно отдельно измерить seed retrieval, adaptive selection, coverage и precision.
2. **Детерминированный базовый слой.** BM25 легко воспроизводится и не скрывает причину ошибки за сложной моделью.
3. **Разделение candidate pool и active budget.** Это основа масштабирования на большие внешние корпуса.
4. **Локальное соседнее расширение.** Boundary context восстанавливается рядом с найденным anchor, а не за счёт передачи большого фиксированного блока.
5. **Сохранение независимых anchors.** Далёкие найденные места не обязаны сливаться в один coarse chunk.
6. **Контроль границ документов.** Соседи не переходят в другой файл.
7. **Кэширование выбранного контекста.** Внешний размер корпуса не должен напрямую раздувать KV-cache.
8. **Отсутствие обязательного обучения.** Рабочий lexical режим не требует подготовки отдельного retriever.

## 7. Ограничения и риски

### 7.1. Precision пока низкая

В тестах система часто находит правильную область, но выбирает вокруг неё много дополнительного контекста. Это полезно для связности, но неэффективно при жёстком active budget.

### 7.2. Chunk budget пока не полностью token-aware

Индексирование рабочих документов ориентируется на символы, тогда как лимит active window задаётся в token-equivalent. Длина реального prompt также включает metadata, разделители и инструкции.

### 7.3. Lexical retrieval зависит от формулировки запроса

BM25 хорошо работает при совпадении терминов, но хуже переносит:

- синонимы;
- морфологические формы;
- перефразирование;
- вопросы, где нужный термин отсутствует в запросе.

Для русскоязычной документации особенно важна последующая проверка морфологии и словаря синонимов.

### 7.4. Соседний radius создаёт trade-off

Увеличение radius не гарантирует улучшение. Соседи помогают восстановить границу chunk, но могут снижать precision и занимать места независимых целей.

### 7.5. Нет полноценного iterative retrieval

Текущая схема выполняет один retrieval pass. Она ещё не умеет после чтения первого слоя уточнить запрос, проверить недостающие факты и добрать контекст вторым проходом.

### 7.6. Синтетические тесты не заменяют реальную документацию

Они хорошо изолируют механизм и позволяют контролировать позиции иголок, но не отражают полностью:

- сложность реальных разделов;
- повторяющиеся термины;
- таблицы и списки;
- ссылки между документами;
- неоднозначные вопросы;
- качество исходной структуры документации.

## 8. Приоритетный план дальнейшей работы

### Приоритет 1: token-aware context accounting

Сделать фактический подсчёт токенов для каждого chunk и всего построенного prompt. Бюджет должен ограничиваться не количеством chunks, а реальным размером контекста с учётом разделителей и служебного текста.

### Приоритет 2: калибровка selector

Провести матрицу прогонов по:

- `chunk size`;
- `candidate-k`;
- `budget`;
- `span_size`;
- `neighbor_radius`.

Оптимизировать не одну recall, а Pareto-компромисс:

```text
target recall ↑
target coverage ↑
context precision ↑
active tokens фиксированы
```

### Приоритет 3: защита anchors при расширении

Ввести отдельные гарантии для:

- первичного anchor;
- соседей boundary repair;
- независимых дополнительных целей.

Сосед не должен вытеснять более важный anchor только потому, что оказался ближе по позиции.

### Приоритет 4: улучшение lexical query

Добавить контролируемые, измеряемые механизмы:

- словарь синонимов документации;
- нормализацию терминов;
- более аккуратную морфологическую поддержку;
- отдельное усиление редких сущностей и параметров.

Каждое такое изменение нужно проверять на фиксированном regression-наборе, чтобы не получить рост recall за счёт резкого падения precision.

### Приоритет 5: реальный annotated benchmark

Собрать небольшой набор обычной документации с разметкой:

- вопрос;
- целевой документ;
- целевой диапазон строк или абзацев;
- допустимый соседний контекст;
- минимальный достаточный набор фрагментов.

Это позволит измерять Native RAG в терминах, близких к реальному использованию: «нашёл ли нужный диапазон документации и сколько лишнего передал».

### Приоритет 6: iterative retrieval

После стабилизации базового selector можно добавить второй pass только для случаев:

- низкая уверенность;
- неполное покрытие нескольких целей;
- вопрос требует связать два удалённых раздела.

Это лучше делать после калибровки однопроходной версии, иначе будет сложно понять, какой слой дал улучшение.

## 9. Итоговая оценка

Текущий Native RAG уже решает основную архитектурную задачу: большой внешний корпус отделён от маленького рабочего окна, поиск выполняется глубже, чем объём передаваемого контекста, а выбранные фрагменты можно префиллить и кэшировать без загрузки всего корпуса в KV-cache.

На контролируемых 1M- и 256k-тестах retrieval находит целевые области стабильно. Главная незавершённая часть RAG — не базовая работоспособность, а точная калибровка active window: сколько соседнего контекста действительно нужно, как сохранить независимые anchors и как повысить coverage без переполнения окна мусором.

Практически проект уже можно считать хорошим исследовательским прототипом. До статуса «нормальный production RAG» ему прежде всего нужны token-aware budgeting, реальный annotated benchmark и систематическая оптимизация precision/coverage.
